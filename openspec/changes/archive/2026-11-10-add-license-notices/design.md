# Design

## Context

See proposal.md (Why) for what ships without notices today. What matters for the approach:

- The binary already embeds three file trees: `web/dist` (`webui.go`, `//go:embed all:web/dist`), `mappings/` (`mappings.go`, which includes `LICENSE-dfc` and `dfc-source.json` with the dfc commit `84e5c1c…`) and `historydata/`. `-refresh-mappings` rewrites `LICENSE-dfc` along with the mappings, so that notice already stays current.
- `web/dist` is gitignored except `.gitkeep`, so anything Vite writes there exists only in builds that ran `npm run build`: release archives (GoReleaser `before` hook), the Docker image (`web` stage) and CI's Docker build. Plain `go build`/`go test` see only `.gitkeep`.
- Vite 8.3.4 (installed) has a built-in `build.license` option. With `fileName` ending in `.json` it writes raw metadata: an array of `{name, version, identifier, text}` for each package with code in the bundle. A trial build on 2026-11-10 listed exactly `@tanstack/query-core`, `@tanstack/react-query`, `react`, `react-dom`, `react-router` and `scheduler` 0.28.0, each MIT with license text (1,078–1,160 characters). `@remix-run/route-pattern` and `cookie-es` were not listed, because no code from them is bundled.
- Go module license files are only reachable at build time (module cache, `go list`). At run time the binary knows its modules and versions (`runtime/debug.ReadBuildInfo`) but has no license texts, so the texts have to be embedded.
- Other run modes that exit without serving (`-version`, `-refresh-mappings`, `-record-history`) are handled at the top of `main`, outside `Service`. This one is neither an MCP tool nor an API endpoint, so it belongs there too.

**No API changes:** the Go server gets a new flag but no new MCP tools or `/api/` endpoints. One side effect: `web/dist/licenses.json` is served as a static file at `/licenses.json`, like every other file in the bundle. It holds public license texts, so that's harmless, and it isn't linked from the UI.

**No new dependencies.** Everything uses Vite's built-in option, the Go standard library and `go list`.

## Goals / Non-Goals

**Goals:**
- One rendering of the notices, used by `-licenses`, `THIRD_PARTY_NOTICES` in archives and the image, so the three can't differ.
- Build-time failure, not silent omission, when any part of the notices is missing or out of date.

**Non-Goals:**
- Detecting license types for Go modules. Entries carry the license files' text; Vite's `identifier` is shown for UI packages because it's free.
- Making `go build` without Node produce complete notices. Such a binary has no UI to give notices for (LN-7.2).

## Decisions

### D1. Go notices: a committed JSON file, generated by a test

`notices/go-notices.json` (embedded with `//go:embed notices`) holds an entry for the Go standard library, then one per linked module, sorted by path: `{path, version, files: [{name, text}]}`, where `files` are the module root's `LICENSE*`, `COPYING*`, `NOTICE*` and `PATENTS*` files in name order. The standard library's entry has no version and reads `LICENSE` and `PATENTS` from `go env GOROOT`.

`TestGoNoticesFile` runs `go list -deps -f '{{with .Module}}…{{end}}' .` (the main package only, so test-only imports never count), collects the non-main modules with their versions and directories, and builds the file in memory:
- With `UPDATE_FIXTURES=1` it writes the file, the same pattern as `TestCatalogFamiliesFixture` and `TestHistoryReportFixture`.
- Otherwise it compares, and on a difference fails with the modules that are missing, extra or at another version, plus the regeneration command (LN-6.1).

Modules are compared by path and version, and the standard library by its texts, not by the toolchain version (LN-6.2). A module's files can't change without its version changing (go.sum pins them), so path and version are enough there.

*Alternatives:* `google/go-licenses` (a new tool to pin and keep current, and it classifies licenses we don't need classified); generating at build time in the GoReleaser hook and the Dockerfile (no committed file to review in a PR, and `go build` alone would carry no Go notices); `go generate` (nothing else in the project uses it, and the fixture-test pattern already gives a staleness check for free).

### D2. Runtime cross-check against the build info

`-licenses` compares the modules in `debug.ReadBuildInfo()` with the module entries in the embedded Go notices, and fails with a non-zero exit, naming the differences, if they disagree (LN-2.3). This catches a release built from a commit whose notices file is stale, for example if a dependency bump was merged without running the tests. Because GoReleaser and the Dockerfile generate `THIRD_PARTY_NOTICES` by running `-licenses`, the build fails too. If the build info is unavailable (not expected from `go build`/`go run`), the check is skipped.

### D3. UI notices: Vite's `build.license` as `licenses.json`

`web/vite.config.ts` sets `build: { license: { fileName: 'licenses.json' } }`, so `npm run build` writes `web/dist/licenses.json`, which the binary already embeds. Go reads it from the embedded UI file system, with a strict decoder for the array of `{name, version, identifier, text}`: an unknown shape is an error, not an empty list. An entry with an empty `text` is an error naming the package, because an entry without the license text isn't the notice the license asks for.

The rule for a missing file (LN-7): if the embedded UI has `index.html` but no `licenses.json`, `-licenses` fails. If the UI has no `index.html` (only `.gitkeep`), it prints a line saying the web UI isn't included in this build.

*Alternatives:* the default `.vite/license.md` (Markdown with Vite's own heading, so the output would mix two formats, and Go couldn't check it); collecting licenses from `node_modules` with our own script (it would have to work out which packages are really bundled, which Vite already knows).

### D4. One plain-text rendering

A new `notices.go` renders everything as plain text, in a fixed order so repeated runs are byte-identical:

1. A header line, `chainguard-mcp <version> third-party notices`, and a sentence saying that the binary includes the components below.
2. The Go standard library, then the Go modules by path.
3. The dfc package mappings, with the commit from `dfc-source.json` and the text of `LICENSE-dfc`.
4. The web UI packages by name, with version and SPDX identifier.

Each entry starts with a separator line and `name version`, then each file as `--- <file name> ---` followed by its text. UI entries have one block, labelled with the identifier, since Vite doesn't give file names.

### D5. Shipping the file

- **GoReleaser:** after the existing web build hook, a hook runs `sh -c 'go run -ldflags "-X main.version={{ .Version }}" . -licenses > THIRD_PARTY_NOTICES'`, so the file's header matches the release binaries' version (LN-4.1). `archives.files` becomes `[README.md, LICENSE, THIRD_PARTY_NOTICES]`. The hook needs `sh`, which the Linux release runner has. `THIRD_PARTY_NOTICES` at the repo root is gitignored, so a local snapshot run doesn't leave it to be committed.
- **Dockerfile:** the build stage runs natively on `$BUILDPLATFORM`, so before cross-compiling it runs `go run . -licenses > /out/THIRD_PARTY_NOTICES`. The final stage copies it to `/THIRD_PARTY_NOTICES`. Both use version `dev`, like the image's binary, so LN-5.1 holds.
- **CI:** the Docker smoke test checks that `-licenses` exits 0, prints `golang.org/x/sync`, `react-router` and the dfc entry, and that `docker cp` of `/THIRD_PARTY_NOTICES` from a created container equals that output. The `Release config check` job lists the snapshot's `linux_amd64` archive and checks it contains `THIRD_PARTY_NOTICES`.

### D6. Tests

- `TestGoNoticesFile` (D1).
- Rendering tests with an `fstest.MapFS` UI, using a `licenses.json` captured from the 2026-11-10 trial build as `testdata/vite-licenses-2026-11-10.json`: every bundled package appears (LN-1.5) and `@remix-run/route-pattern` doesn't (LN-2.1); `index.html` without `licenses.json` fails (LN-7.1); `.gitkeep` only prints the "not included" line (LN-7.2); an entry with empty text fails; output is identical across runs.
- A test that the Go notices contain the `PATENTS` text for `golang.org/x/sync` and the go-sdk's transition paragraph (LN-1.1, LN-1.2), the standard library entry (LN-1.3) and the dfc commit (LN-1.4), and no development tooling (LN-2.2).
- The build-info comparison as a pure function, with fake module lists (LN-2.3).
- `-licenses` itself through a test that builds and runs the binary, so the exit status, the header and "no network" are checked end to end (LN-3.1).

## Risks / Trade-offs

- [A dependency bump is merged without regenerating] → `TestGoNoticesFile` fails in CI on the PR, and D2 fails the release if it gets through anyway.
- [Vite changes the `licenses.json` shape in a later major] → the strict decoder fails the build with a clear message instead of shipping empty notices; the testdata fixture is regenerated when upgrading Vite.
- [A bundled npm package has no license file, so Vite gives no text] → the build fails naming the package. If that ever happens, the fix is a small table of license texts kept in the repo for that package, decided then.
- [`/licenses.json` becomes publicly reachable on any deployed server] → it holds public license texts only; accepted.
- [The GoReleaser hook depends on `sh`] → releases and CI's snapshot run on Linux. A local Windows snapshot would need Git Bash's `sh` on `PATH`, which is noted in CLAUDE.md.
- [`go list` in a test needs the module sources] → they're already in the module cache for `go test` to build the package, so no extra download.

## Migration Plan

Nothing to migrate. The first release after this change ships the file; older releases stay as they are.
