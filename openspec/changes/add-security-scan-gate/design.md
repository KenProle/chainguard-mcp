# Design

No API changes: the Go server, the web API and the UI are untouched. All new code is CI tooling and does not ship in the binary or the image.

## Context

See proposal.md - Why. Facts that shape the approach:

- **CI today.** `vulncheck.yml` is the model for a single-purpose workflow with one named job that the `Protect main` ruleset requires. `workflows_test.go` pins such files with line-level text checks.
- **The scan.** Spike on 2026-11-10 (scratch clone at commit 8a6d75c, Sonnet 5.5, low effort): it runs headless only when (a) Claude Security is the *main* agent (`--agent claude-security:claude-security`; as a subagent it lacks the Workflow tool), (b) `enableWorkflows` is set (`--settings '{"enableWorkflows": true}'`), (c) the prompt itself accepts the time and token cost, and (d) tools are allowed explicitly. Result: 18 files, 1,040 lines, 1 researcher, 84 s, list-price $0.39, no findings. It wrote `CLAUDE-SECURITY-RESULTS.sarif`, `.jsonl`, `.md` and `CLAUDE-SECURITY-REVISION-<sha12>.json`. The stamp holds `findings.{critical,high,medium,low,total}` and `verification.{status,researchers_dispatched,researchers_returned,reason}`. The SARIF `results` was empty, so the shape of a real finding, and whether findings predating the change appear in it, are not yet observed.
- **GitHub.** Security tab alerts need write access; pull request annotations from code scanning are visible to anyone with read access (docs.github.com, checked 2026-11-10), which on this public repository is anyone. The user accepted that. GitHub withholds repository secrets from pull requests that come from forks, and gives Dependabot runs a separate secret store.
- **Auth.** There is no API key. `claude setup-token` makes a one-year OAuth token for a Pro/Max/Team/Enterprise subscription; it can only make model requests. The action takes it as `claude_code_oauth_token`.

## Goals / Non-Goals

**Goals:** a required check that blocks verified high/critical findings in security-sensitive changes; fail closed whenever the scan cannot vouch for itself; no secret reaches code the owner has not reviewed; everything that can be tested without GitHub (path decision, verdict) is tested here, on Windows too.

**Non-Goals:** replacing the three manual reviews (they still run before merge); scanning forks; whole-repository scans; auto-fix patches; comments on the pull request other than code-scanning annotations.

## Decisions

**1. One job that always runs; the decision is a step inside it.** The job is named "Security scan", triggers on `pull_request`, and its first steps decide whether to scan. Rejected: a workflow-level `paths:` filter (a required check whose workflow never starts stays "pending" forever and blocks the merge), and a job-level `if:` (a skipped job's status in a required-check context is easy to misread; one job that ends in an explicit pass is simpler to reason about and test).

**2. Path list in a file, decision in a small Go program.** `.github/security-scan-paths.txt` lists patterns (one per line, `#` comments). `scripts/securityscan.go` (`//go:build ignore`, run with `go run`) has two subcommands: `decide` reads changed file names on stdin, with the base repository, head repository, author and actor as flags, and prints `decision=` (`scan`, `skip`, `skip-dependabot` or `fail-no-token`) and `reason=` lines, never raw file names, because the output goes to `$GITHUB_OUTPUT`; the file list is NUL-separated (`git diff -z`) so odd file names stay whole; `verdict <stamp.json>` applies SG-4 and prints a Markdown summary. Initial list: `*.go` except `*_test.go`; `web/src/**` except tests; `Dockerfile`, `.dockerignore`, `.goreleaser.yaml`; `.github/**` (the workflows, Dependabot, this list); `go.mod`, `go.sum`, `web/package.json`, `web/package-lock.json`, `web/vite.config.ts`; `mappings/**` and `notices/**` (embedded data); `.claude/**`, `CLAUDE.md`, `.mcp.json`. Skipped: `openspec/**`, `docs/**`, `site/**`, `README.md`, `*_test.go`, `testdata/**`. Rejected: shell plus `jq` (not reliably on the Windows dev machine, so not testable there); content patterns such as "diff mentions `os/exec`" (more code, easy to evade, and the path list is reviewable); a path-filter action such as `dorny/paths-filter` (a new dependency for ten lines of logic); a new run mode in the shipped binary (keeps CI tooling out of what users run). Unlisted new top-level files default to *scan*, so adding a file type cannot silently skip.

**3. Checkout the head commit, scan against the base.** `actions/checkout` with `ref: <head sha>` and `fetch-depth: 0`, then the scan runs as "scan the changes on this branch against `<base sha>`". The default pull-request checkout is a merge commit, which can make the range include unrelated base changes. This is safe for `pull_request` (fork code gets no secrets, SG-6); it would not be for `pull_request_target`, which is why that trigger is banned and the test checks for it.

**4. The action runs the scan, with Claude Security as main agent.** `anthropics/claude-code-action` inputs: `claude_code_oauth_token`, `github_token: ${{ secrets.GITHUB_TOKEN }}` (so no GitHub App install is needed), `plugin_marketplaces: ${{ runner.temp }}/marketplace` (a local path, which the action accepts; a plain `git clone` of `anthropics/claude-plugins-official` checked out at the pinned commit `ca08d5e47d6402db586d37780c559a0c4c7ded9a` in the step before, because the action's URL form takes no commit), `plugins: claude-security@pinned-plugins` (Claude Code refuses the name `claude-plugins-official` for anything but the GitHub source, and refuses any name that looks like an official one, such as `claude-plugins-pinned`; both showed up on PR 15's first two runs, so the pinned copy's `marketplace.json` name is rewritten with `jq` to the neutral `pinned-plugins` after the checkout, and adding it and installing the plugin were confirmed locally with a throwaway config directory), `settings: {"enableWorkflows": true}`, and `claude_args` with `--agent claude-security:claude-security --model <chosen> --allowedTools "Bash Read Write Edit Glob Grep Workflow Agent"`. The prompt carries the cost acknowledgment the plugin requires ("I understand this scan may take a long time and use a significant number of tokens"); the plugin accepts that only from the user's own request, and the workflow file is the repository owner's request. Whether the action passes `--agent` through and still runs the plugin's pre-approved helper commands is **unverified**; task 4.1 proves it on this change's own pull request before anything depends on it. Fallback if it does not: install the Claude Code CLI with npm in the step and call `claude -p` as in the spike (one more dependency, justified then). Rejected for now: a hand-rolled `claude -p` from the start (more to maintain than the action).

**5. Verdict is computed from the stamp, not from the model's words.** The stamp's counts and `verification.status` are computed in code by the plugin, per its README. `verdict` fails closed on: missing or unparseable stamp, `status != verified`, `researchers_returned < researchers_dispatched`, any critical or high. It prints counts and the verification line to the job summary. Medium and low are listed, not blocking, because scans are nondeterministic and a gate that blocks on low-confidence output would be re-run until it passes.

**6. SARIF upload, with the "predates the change" rule.** `github/codeql-action/upload-sarif` (GitHub-owned; pinned to a commit like every action here since the DV-8 rule landed on `main`, v4.39.1 of 2026-10-21, the newest release over two weeks old; v4.39.3 of 2026-11-04 ran fine before the pin but is too recent to adopt; Dependabot's monthly Actions group bumps the SHA), `category: claude-security`, `if: always()` after the scan step so the findings that fail the job are still shown. Per the plugin's scan-changes recipe, candidates real but predating the change are reported in the coverage section, not as findings, so they should not be in the SARIF; task 4.3 confirms this on a real finding, and if they are present the `verdict` program filters them out before upload and counts them in the summary. Credentials are not quoted in the SARIF (plugin README), and a credential committed in a pull request is already public in its diff, so the remedy there is rotation, not hiding the annotation.

**7. Pull requests that cannot be scanned.** Fork pull requests get no secrets: if `needed` says scan, fail with a message (SG-6.1); otherwise pass. Dependabot pull requests that change only `.github/workflows/` pass without a scan (SG-11): giving Dependabot the token would mean the unreviewed, bumped version of `claude-code-action` itself runs with it, which is worse than leaving that one monthly pull request to the human review it already gets. Rejected: adding the token as a Dependabot secret; excluding workflow changes from the path list (workflow changes are among the riskiest files).

**8. Claude configuration comes from the base branch.** The action restores `.claude/`, `.mcp.json`, `.claude.json`, `CLAUDE.md` and a few others from the base branch before starting Claude on a pull request (docs/security.md in the action's repo, read 2026-11-10), which is the fix for GHSA-8q5r-mmjf-575q (a pull request's `.mcp.json` ran code on the runner; patched in 1.0.74). SG-7 depends on that behavior, so task 4.4 tests it with a throwaway pull request that adds a `.mcp.json`.

**9. Pin the action to a commit.** Every action in the repo is pinned to a commit now (DV-8, merged to `main` while this change was in review, which also pins `actions/checkout` v7.0.1 and `actions/setup-go` v7.0.0 here to the SHAs the other workflows use); this one matters most, because it holds the token and runs code from the checkout. Version chosen: v1.0.263 (released 2026-10-26, so over two weeks old; the newest, v1.0.271, was released the day of this review and releases come about every two days). Commit `8041f1d17e0e7d2f2cfe35002962e9f26237c0bb` resolved from the tag through the GitHub API on 2026-11-10; re-resolve it when implementing. Dependabot's monthly Actions group will open a pull request bumping the SHA and its version comment; that pull request is the SG-11 case.

**10. Rollout in two steps.** Merge the workflow *without* requiring it; watch it on at least three real pull requests (SG-4 verdicts, run time, usage); then add "Security scan" to the ruleset (SG-9). Requiring it before it has reported on `main` would block every pull request.

## Risks / Trade-offs

- **Usage limits on a Pro plan.** Each scan draws on the owner's personal allowance; many risky pull requests in a day could exhaust the five-hour window, including for interactive work. → Medium effort only; narrow path list; measure real usage in task 4.5 before requiring the check; a rate-limited scan fails closed with its reason, and can be re-run later.
- **Expiring or revoked token.** The OAuth token lasts a year and belongs to the owner's subscription. → Every risky pull request fails closed with "token invalid"; the creation date and renewal steps go in `CLAUDE.md`; a calendar reminder is set at renewal.
- **Prompt injection exfiltrating the token.** The scan reads attacker-influenced text (the diff) while holding the token in its environment, and its tools include Bash. → Only same-repository pull requests get a scan (write access required), the token can only make model requests, and task 4.4 checks whether the Bash tool can read it; if it can, the workflow sets the action's subprocess scrub for that step.
- **Nondeterminism.** Two scans of the same diff can disagree, so a pull request may fail once and pass on re-run. → Accepted; fix the finding or re-run, and a verified high that appears once is worth reading either way.
- **Weak assurance at the edges.** A clean result is a model's reading of the diff, not proof; the summary says "no verified findings", never "secure". The three manual reviews still apply.
- **Plugin updates.** The action's marketplace input takes a bare Git URL with no commit, which would follow the default branch and let the scan change without a pull request here. → Checked in task 1.3: the workflow instead clones the marketplace at a reviewed commit and passes the local path, so the scan changes only when someone edits that commit in the workflow. The cost is that new plugin versions are adopted by hand; check the plugin's release notes when bumping.
- **Public annotations.** Findings in a pull request are visible before the fix is pushed (accepted by the user, limited to the pull request's own changes by SG-5 and SG-10).
- **The pull request supplies the gate's own code.** A `pull_request` run uses the workflow file from the pull request, and `go run scripts/securityscan.go` runs the pull request's copy, so a pull request that edits either can weaken its own check. `pull_request_target` would use the base's workflow but is banned (SG-6), and organization-level required workflows are not available to a personal repository. → These files are in the path list, so such a change is itself scanned, and it gets the three manual reviews, where the diff to the workflow is what the reviewer reads first. SG-12 limits the other half of the same trick (a planted result) but cannot close this one.
- **Cancelled runs.** A new push cancels the running scan (SG-1.2); the new run replaces it, so no cancelled result is left as the required check.

## Migration Plan

1. Merge the change with the workflow present but not required; add the `CLAUDE_CODE_OAUTH_TOKEN` secret first.
2. Run the staged checks (tasks 4.x): this change's own pull request, a docs-only one, and throwaway pull requests with a planted flaw and a `.mcp.json`.
3. Add "Security scan" to the `Protect main` ruleset.

Rollback: remove the check from the ruleset, then delete the workflow. Nothing else depends on it.
