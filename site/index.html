Why your assistant needs it

Moving a Dockerfile to Chainguard images means answering questions an assistant can’t reliably answer from memory, so without live data it guesses. Some guesses fail the build; others install and break later.

  • Package names differ. Of 59 apt packages commonly installed in Dockerfiles, 27 have the same name in Wolfi, the distribution Chainguard images are built from (measured 2026-10-19).
  • Plausible answers can be wrong. Mapping libssl-dev to libssl3 installs the runtime library but not the headers; the build needs openssl-dev.
  • Version tags need a subscription. The free tier publishes latest-style tags, so node:20 can’t simply become cgr.dev/chainguard/node:20.
  • The images work differently. They run as a non-root user, and the minimal variants have no shell or package manager.

chainguard-mcp gives the assistant tools that read the answers from Chainguard’s registry, the images’ signed SBOMs and Wolfi’s package index instead.

Install

1. Get the binary. Download the build for your platform from the latest release and put it somewhere permanent. Or install it with Go 1.27 or later:

go install github.com/KenProle/chainguard-mcp@latest

A go install build has the MCP tools but no web UI; the release binaries include it. The binary lands in $(go env GOPATH)/bin.

2. Add it to your client. Use the full path to the binary in place of /path/to/chainguard-mcp. On Windows that is the .exe file, and backslashes in JSON are doubled (C:\\tools\\chainguard-mcp.exe).

Claude Code 
claude mcp add -s user chainguard -- /path/to/chainguard-mcp

Run it once in a terminal. -s user makes the server available in all your projects.

Cursor

Add this to ~/.cursor/mcp.json (or .cursor/mcp.json in one project):

{
  "mcpServers": {
    "chainguard": {
      "type": "stdio",
      "command": "/path/to/chainguard-mcp"
    }
  }
}
Claude Desktop

Open Settings, then Developer, then Edit Config. The file is claude_desktop_config.json (~/Library/Application Support/Claude/ on macOS, %APPDATA%\Claude\ on Windows). Add the server, then quit and restart Claude Desktop:

{
  "mcpServers": {
    "chainguard": {
      "command": "/path/to/chainguard-mcp"
    }
  }
}
VS Code

Add this to .vscode/mcp.json in your workspace (or the mcp.json in your user profile):

{
  "servers": {
    "chainguard": {
      "type": "stdio",
      "command": "/path/to/chainguard-mcp"
    }
  }
}

Ask your assistant

Four questions that follow a migration, with the answers shortened from real tool output. Your assistant picks the tools itself and often chains several.

“What Chainguard image should replace node:20?”

The find_alternative tool answered, 2026-10-20:

recommended: cgr.dev/chainguard/node   (free tier)
related:     node-fips                 (subscription)
notes:  use :latest-dev for build stages and :latest for runtime;
        the free tier only provides the latest version, so pin
        :latest by digest for reproducible builds

“How does it compare with what I run now?”

The compare_with_upstream tool compared node:20 from Docker Hub with cgr.dev/chainguard/node:latest on 2026-10-20 (amd64); the numbers are in the comparison below. It also noted that Node.js 20 reached end of life on 2026-04-30.

“Pin it for my Dockerfile.”

The pin_image tool answered, 2026-10-20 (digest shortened):

cgr.dev/chainguard/node:latest@sha256:95f685867310…

“Migrate this whole Dockerfile.”

The migrate_dockerfile prompt takes your Dockerfile and walks the assistant through these steps, as of 2026-10-20 (shortened): choose an image for each FROM with find_alternative, check its user and entrypoint, use a build stage on :latest-dev and copy into the minimal :latest, map apt-get packages to apk names with map_packages, fix file ownership for a non-root user, and pin each final image with pin_image. It returns the new Dockerfile and a list of what needs manual testing.

What else you can ask

  • “What free Chainguard images are there for Python?” list_images
  • “Does the python image run as root? Which architectures does it support?” get_image_details
  • “Does python have a shell? What about latest-dev?” get_image_packages
  • “Which tags can I pull for nginx?” get_image_tags
  • “Is the python image affected by CVE-2022-3602?” check_vulnerabilities
  • “Save the SBOM for nginx so I can scan it.” save_sbom
  • “Which apk packages replace my apt-get line?” map_packages
  • “What did Chainguard add to its catalog this month?” catalog_changes

Example: upstream against Chainguard

Each image is graded by its own maintainers’ advisories, and the counts are known vulnerabilities only, not a guarantee about either image. A count of 0 means none were known to those sources on that date.

The Chainguard side is always the free latest tag, which can be a newer release than the upstream tag: on that date it was Node.js 26 against node:20, and Python 3.15 against python:3.12-slim. Chainguard rebuilds its images constantly, so run the comparison yourself for current numbers. Only installed OS packages are compared. Language packages are counted but not compared, and the Linux kernel is left out because containers run on the host’s kernel.

What it reads

  • The signed SBOM attached to each Chainguard image, and the SBOM that Docker Hub publishes for upstream images.
  • Chainguard’s advisory feed, for the status of each advisory on its own images.
  • OSV.dev, for known vulnerabilities by package.
  • Wolfi’s package index, to check the package names it suggests.
  • endoflife.date, for support end dates.

The open advisories it lists for Chainguard images were also checked against the scanner grype. Grype reported only the OS vulnerabilities that Chainguard has not yet assessed, and this tool lists those too, together with the ones waiting for an upstream fix.

The web UI

Run the binary with -http 127.0.0.1:8080 to browse the same data in your browser.

Limits

  • Detail tools work for free tier images only, and the free tier’s public tags are latest-style. Subscription-only images get a clear message.
  • Upstream comparisons cover Docker Hub images only, and only those that publish an SBOM.
  • Only OS packages are compared. Language packages are counted, not compared.
  • Vulnerability counts are known vulnerabilities from public advisories, not a scan of the image.

Chainguard’s own documentation server

Chainguard runs a documentation MCP server, hosted at mcp.edu.chainguard.dev, for questions about its docs; see its AI Docs page. This project complements it: it answers questions about specific images, their packages and how they compare, using the public image data rather than the documentation.
